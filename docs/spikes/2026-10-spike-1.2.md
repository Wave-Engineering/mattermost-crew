## 1. Enterprise Entry's own limits

**Source.** The vendor's
[Editions and Offerings](https://docs.mattermost.com/product-overview/editions-and-offerings)
page lists Entry's limits: "10,000 Channel messages history across all channels"; "older
messages remain in the database but aren't viewable or searchable". Also 1000 board cards,
5 playbook runs a month, 250 agent queries a month, 40-minute calls and 10,000 push
notifications a month, which are starred as taking effect "in a future release". There are no
compliance features, delegated admin roles or HA. The page names no limit on bots, personal
access tokens, token expiry, API access, users, teams or channels. Entry "is best suited for
teams less than 50 users". The [FAQ](https://docs.mattermost.com/product-overview/faq-general)
adds that the history limit applies to "the end user interface for channel history and search"
and that all records stay in the database.

**Check.** No licensed image is available to us, but question 5 shows that the unlicensed
Enterprise image *is* Entry. Its own server-limits endpoint reports the cap:

```
$ curl -H "Authorization: Bearer $MM_ADMIN_TOKEN" $MM_URL/api/v4/limits/server
enterprise-edition 11.11.3: {"maxUsersLimit":0,"maxUsersHardLimit":0,"activeUserCount":1,"singleChannelGuestCount":0,"singleChannelGuestLimit":0,"postHistoryLimit":10000,"lastAccessiblePostTime":0}
team-edition 11.11.3:       {"maxUsersLimit":200,"maxUsersHardLimit":250,"activeUserCount":13,"singleChannelGuestCount":0,"singleChannelGuestLimit":0,"postHistoryLimit":0,"lastAccessiblePostTime":0}
team-edition 11.8.5:        {"maxUsersLimit":200,"maxUsersHardLimit":250,"activeUserCount":10,"singleChannelGuestCount":0,"singleChannelGuestLimit":0,"postHistoryLimit":0,"lastAccessiblePostTime":0}
```

Bot accounts do not count toward Team Edition's user limit: the 11.11.3 server above had 13
humans and 12 bot accounts (`GET /users?include_bots=true`), and reported `activeUserCount: 13`.

**Answer:** Entry caps visible history at the newest 10,000 posts across all channels (server
`postHistoryLimit: 10000`); older posts remain stored but are not returned to reads or search.
That affects the read path only for posts older than that window, and it is detectable at
runtime from `GET /api/v4/limits/server` (`postHistoryLimit`, `lastAccessiblePostTime`), as CT-01
requires. Nothing else in Entry's list touches bots, tokens or the API the program uses. On Team
Edition, bot accounts don't count toward the 200/250 user limit, so a crew's agents don't use
up human seats. No design change. **[ledger D-093]**

## 2. One client per token in one process

**Command.** `uv run --no-project --with mcp-server-mattermost==0.6.1 spikes/two_clients.py`
against Team Edition 11.11.3. `MattermostClient(settings, token=...)` takes a per-client token
override. The script builds two clients with two bot tokens, posts once from each on its own
connection pool, then posts 10 times from each concurrently while both borrow one shared
`httpx` pool (`http_client=`), which is how the daemon would hold about 30.

**Output** (`evidence-1.2/two_clients.txt`, abridged):

```
upstream: mcp-server-mattermost==0.6.1
ok  own pool    client one      get_me=hpazd9msafb97dqjs5e73xecgy post.user_id=hpazd9msafb97dqjs5e73xecgy
ok  own pool    client two      get_me=dtk3adhimbgb9y8mkh961fb9uo post.user_id=dtk3adhimbgb9y8mkh961fb9uo
ok  shared pool client one#0    get_me=hpazd9msafb97dqjs5e73xecgy post.user_id=hpazd9msafb97dqjs5e73xecgy
ok  shared pool client two#0    get_me=dtk3adhimbgb9y8mkh961fb9uo post.user_id=dtk3adhimbgb9y8mkh961fb9uo
...
22 posts, 0 with the wrong author
```

It passed three runs in a row. **One usage rule surfaced.** An earlier version of the script
entered and left the *same* client object's `lifespan()` from several concurrent tasks. It
passed once, then failed with `RuntimeError: Client not initialized`, because the first task to
leave sets the client's `_client` to `None` under the others. The daemon must enter each
client's `lifespan()` once and hold it open for that token's life, and not open a lifespan per
call. The script now does exactly that.

**Answer:** Yes. The upstream library supports one client object per token in one process, on
separate pools and on one shared pool, with no author mix-up under concurrency. The token travels
per request, never in the shared pool's default headers. `Settings` needs
`auth_mode=client_token` (or a placeholder token) when the token is per client. Each client's
`lifespan()` must be entered once and held, never entered concurrently per call. §5.2 (D-054)
stands. **[ledger D-094]**

## 4. The kiosk mechanism

### (a) The CLI runner

### (b) A direct model API call with no tools

Not run directly. There is no OaW Anthropic API key on this host, and the subscription login is
for Claude Code only, so it can't be used for a direct API call. The CLI measurement bounds it
anyway: the CLI sends no tool definitions (`tools_sent: 0`) and a system prompt of 4,504
characters, so a direct call with the same brief and question costs the same API time (about
3.3 s) and roughly the same money. Output tokens are most of the cost and would be the same.
What (b) saves is the CLI's ~1.7 s of start-up. `spikes/kiosk_api.py` is the harness for
measuring (b) directly once a key exists: one Messages API request per run, the same brief and
question, and no `tools` field
(`ANTHROPIC_API_KEY_FILE=<path> uv run --no-project --with httpx spikes/kiosk_api.py 3`).

### The choice

**The CLI runner, (a).** It is fully measured, and the isolation is proven from the CLI's own
evidence. It also keeps the two credentials apart in both directions: `crewkiosk` holds the
model credential and no chat or broker credential, and `crewchat`, which holds every token, never
holds the model credential. With (b) the daemon would make the call, so `crewchat` would hold the
model key next to every chat token. The ~1.7 s start-up is irrelevant for a kiosk reply. (b)
stays the fallback if the CLI ever stops honouring `--restricted` as measured here.

Conditions the kiosk depends on, for the runbook (Story 3.7):

1. **No managed settings on the kiosk host:** `/etc/claude-code` absent.
2. **No remote managed settings either.** The CLI fetches org-managed settings for the
   credential's account ("Remote settings: No settings found (404)"), and they would apply like
   local managed settings. The kiosk's credential must belong to an account whose organisation
   pushes no managed settings. A verify step greps the kiosk's debug output for that line.
3. **HOME is empty at install, not forever.** The CLI writes `~/.claude.json`,
   `~/.claude/remote-settings.json` and a session transcript under `~/.claude/projects`. The
   runner should pass `--no-session-persistence`, because the daemon keeps the kiosk transcript
   itself (§5.11).
4. **A privilege bridge from `crewchat` to `crewkiosk`** (one wrapper under a sudoers rule, or a
   systemd unit) is needed so the daemon can start the CLI as `crewkiosk`. That belongs to the
   Phase 3 kiosk story, not this spike.

**The kiosk's model credential:** `/etc/crewkiosk/model.credential`, mode `0600`, owner
`crewkiosk:crewkiosk`, holding one line, the key alone, which the runner loads into the CLI's
environment as `ANTHROPIC_API_KEY`. (Corrected by #116: this read `ANTHROPIC_API_KEY=<key>`, but
the runner takes the whole first line as the key. It now also accepts that form and refuses any
other line holding an `=`.) The key is a dedicated, spend-limited Anthropic API key in an OaW
organisation with no managed settings, provisioned by BJ. It is not a chat or broker credential:
neither `crewchat`, `crewbroker` nor the agent's user can read it, and `crewkiosk` can read no
other credential (`make verify-install`, §5.B step 6). This spike's runs used a stand-in: the
operator's own Claude Code login, passed only into the throwaway container's environment and
never written to a file inside it.

**Answer:** The kiosk is the CLI runner, `claude -p --restricted --strict-mcp-config --tools ""
--disallowedTools "mcp__*"` as `crewkiosk`. It ran no shell command, and the CLI's own transcript
and debug log show that no user, project or local settings, hooks, skills or `CLAUDE.md` loaded,
against planted ones in every location, while a planted managed hook and managed `CLAUDE.md` did
load until `/etc/claude-code` was removed. Measured: about 5.4 s and $0.003 per question
(Sonnet). Its model credential is `/etc/crewkiosk/model.credential` (`0600`,
`crewkiosk:crewkiosk`), a dedicated Anthropic API key, readable by no other user. The host must
have no local or remote managed settings. Resolves D-071. **[ledger D-096]**

## 7. Broker transport and trust across hosts: design note

Not built in this Plan. Today every broker the daemon uses is on its host, behind a unix socket,
and a trusted crew whose broker is elsewhere is treated as outsiders (§5.6, §5.9). This is the
shape for a later Plan.

**What crosses hosts: only `crew_info`, and optionally `switch_state`.** `mint`, `remint` and
`revoke` never cross a host, because tokens never leave the host whose daemon uses them. A remote
broker therefore exposes a read-only subset of the socket protocol.

**Transport: mutual-TLS TCP, same frames.** The remote broker listens on
`tls://<host>:<port>` with the same JSON-lines frames and `"proto": 1` (§5.4). Each side pins
the other:

- The broker presents a server certificate issued by the broker's crew CA. The daemon pins that
  CA per trusted crew, in `servers.toml`:

  ```toml
  [crews.<name>.<server_id>]
  broker_url = "tls://broker.example.lan:7443"
  broker_ca = "/etc/crewchat/trust/<name>-ca.pem"
  broker_user_id = "<that crew's broker account id>"   # pinned, as today
  ```

- The daemon presents a client certificate from its own crew's CA, and the remote broker's
  config lists which client identities (certificate subject plus issuing CA) may call
  `crew_info`. That is the cross-host equivalent of the `SO_PEERCRED` check: only a daemon its
  human partner trusts can read its membership.
- The remote broker returns `crew_info` with an `as_of` timestamp and its own `broker_user_id`.
  The daemon rejects a reply whose `broker_user_id` differs from the pinned one.

**Failure semantics: unchanged.** There is a 2 s timeout, and the last good `crew_info` is kept
on a timeout. A never-fetched remote crew is unresolvable (`DROP` for its bot accounts, outsiders
for its humans). The cache-miss re-fetch keeps its once-per-30 s cap, and is never faster for a
remote broker.

**Verifying ownership remotely.** Question 8 shows that only a bot's owner can read its
`owner_id`, so a remote crew's `minted_bot_ids` must already be filtered to the bots that broker
still owns (D-100). The daemon can't check a remote crew's bot ownership itself.

**Keys and rotation.** Each crew runs a small CA, or uses the organisation's existing PKI. Leaf
certificates are short-lived (days) and re-issued by the broker's daily job. Exchanging the CA
certificates is the trust handshake between human partners, done once, out of band.

**Alternative considered:** publishing a signed `crew_info` through Mattermost itself (a pinned
post by the broker account) avoids a new network path, but it adds a signing key and a staleness
problem and lets any channel member read membership. mTLS is simpler and more private.

**Answer:** For a later Plan: a remote broker serves only `crew_info` (and optionally
`switch_state`) over mutual-TLS TCP with the same frames, pinned per trusted crew by CA and
`broker_user_id` in `servers.toml`, with the same timeout and caching rules. Tokens never cross
hosts. This Plan keeps trust same-host only. **[ledger D-099]**

## 8. Bot `owner_id`

**Command.** `spikes/bot_owner.sh` against Team 11.11.3 (`evidence-1.2/bot_owner-team-11.11.3.txt`).
The broker is an ordinary user given the patched `system_user_access_token` role (`create_bot`,
`read_bots`, `manage_bots`), as the design has it. The observer and the new owner are plain
users.

**Output** (summary block; the full request/response log is in the evidence file):

```
PASS  role patch applied  (PUT /roles/{id}/patch -> 200)
PASS  role assigned to broker  (PUT /users/{id}/roles -> 200)
PASS  owner_id set to the creator  (POST /bots -> 201, owner_id=<broker>)
PASS  owner_id readable by its owner (broker)  (broker GET /bots/{id} -> 200)
FAIL  owner_id visible to another user  (observer GET /bots/{id} -> 404, bot GET /bots/{id} -> 404)
PASS  bot cannot change its owner  (assign->observer 404, assign->self 404, PUT /bots owner_id 404; owner after: <broker>)
PASS  owner can reassign the bot  (POST /bots/{id}/assign/{user} as broker -> 200; owner now <newowner>)
PASS  former owner no longer sees the bot  (broker GET /bots/{id} after reassignment -> 404)
```

and the detail behind the FAIL:

```
GET /bots/<bot a>  as observer -> 404 store.sql_bot.get.missing.app_error
GET /users/<bot a> as observer -> 200 {"is_bot":true,…}
user object keys: ["auth_data","auth_service","create_at","delete_at","disable_welcome_email","email","first_name","id","is_bot","last_name","locale","nickname","position","roles","timezone","update_at","username"]

GET /bots?per_page=200 as broker -> 200 [{"user_id":"<bot a>","owner_id":"<broker>"},{"user_id":"<bot b>","owner_id":"<broker>"}]
```

**Answer:** Three of the four facts §5.9 needs hold. `owner_id` is set to the creating broker
account. The bot cannot change it: the bot gets 404 on every bots endpoint for itself, and
`owner_id` is unchanged after. The owner can reassign it (`POST /bots/{id}/assign/{user}`, 200),
after which the former owner can no longer see it (404). **But `owner_id` is not visible to other
users.** `GET /bots/{id}` returns 404 to anyone without `read_bots` on that bot (only its owner)
or `read_others_bots` (admins). The user object carries `is_bot` and no owner. So the daemon,
holding only bot tokens, can't read any bot's `owner_id`, and §5.9's "`owner_id` equals X's
broker" can't be checked by the daemon.

This changes D-079's membership rule (and D-087's cache-miss trigger), so the ledger entry
supersedes them in part. Ownership is verified where it is readable, in the broker:

- `crew_info.minted_bot_ids` is the bots this broker created **and still owns**. The broker
  intersects its minted list with `GET /bots` (its own bots, with `owner_id`) whenever it builds
  `crew_info`. A reassigned bot drops out, because the broker no longer sees it.
- A bot account is in crew X if and only if its user ID is in X's `crew_info.minted_bot_ids`.
  Both of D-079's conditions are kept, and the broker checks the ownership half.
- **Cache-miss trigger:** a sender with `is_bot: true` that is in no cached `minted_bot_ids` (ours
  or a local trusted crew's) causes one re-fetch of every local broker's `crew_info` before any
  verdict, capped at once per bot account ID per 30 s. While any local broker (ours or a trusted
  crew's) has no cached `crew_info`, an unrecognised bot account is `DROP`, never `KIOSK`. That
  keeps D-087's fail-closed intent for a never-fetched trusted crew.
