## 2. MCP server survey (about 25 candidates)

- **No MCP server does push.** None has a websocket or event subscription; all are REST
  request-and-response. **[src]**
- Only bridges, channel plugins and extensions open the websocket:
  - OpenClaw `extensions/mattermost` (MIT): the best reference for reconnect and multi-account.
  - huyeon123/mattermost-claude-channel (no license): Claude Code channel pattern; read it only.
  - Wldc4rd/gc-mattermost-pack: no TLS.
- **ADOPTED for tools (BJ):** `cloud-ru-tech/mcp-server-mattermost`.
  - Python, MIT, v0.6.1 on PyPI, 48 stars, actively pushed. About 5.4k lines.
  - Tools: channels, messages, posts, users, teams, files, bookmarks.
  - Auth modes: `STATIC_TOKEN`, `CLIENT_TOKEN` (HTTP, a bearer per request, verified against `/users/me` with a 60 s cache), OAuth.
  - `MATTERMOST_EXTRA_CA_CERTS` helps behind TLS-intercepting proxies.
  - One `MATTERMOST_URL` per process.
  - Provenance: Cloud.ru, a Russian cloud provider. BJ accepted it; pin a reviewed version and don't auto-update.
- Runner-ups: the official `mcpserver` (rebuild from a pinned tag), vriesdemichael/mm-mcp (Go, well built, only 12 days old).

## 3. Doorbell audit (watcher `4dae4fa`, kit `8515c53`, scream-hole `680c746`)

**Verdict: one multi-backend doorbell is realistic.**

**Coupling**
- Watcher (3,010 lines): about 1,740 neutral, 470 Discord-only, 810 mixed (neutral logic typed on Discord shapes).
- All Discord REST goes through **one function** (`apiGet`, index.ts:802), called from 7 sites.
- scream-hole: its polling cache (about 1,100 lines) is Discord-only and retires. Its leases (about 125 lines) are neutral, and nothing calls them.

**Proposed adapter interface**
- `ChatBackend { id, caps{selfByAccount, serverMentions, threads, dms}, connect(cursor, signal), events(): AsyncIterable<BackendEvent>, selfIdentity(), health(), cursor(), fetchMessage?, fetchAttachment?, close() }`
- `InboundMessage { backend, id, createdAt, channel{id,name,kind}, threadRootId, author{id,name,isSelf|null}, text, replyTo, mentionsSelf?, attachments[] }`
- No send hook: sending stays with the chat servers.

**Size:** about 1,700 lines retyped, 550 moved, 600 rewritten (two loops become one), 600–800 new for the Mattermost adapter, 200 new (cursors, `--once`, merged health). Two to three waves. Keep the `discord-watcher` binary name or an alias: about 27 kit files reference it.

**Hard parts**
- `@name.crew` is stripped to `@namecrew` by the token cleaner (index.ts:890).
- Server-side mentions cover real accounts only. `@<dev-team>` and crew names aren't accounts, and user groups are a paid feature.
- **Our `@all` collides with Mattermost's `@all`**, which pages every human in the channel.
- Each websocket receives every post in the agent's channels, so the in-process filter remains the storm guard.
- Mattermost thread replies point at the root, not a message: "reply to me" means a post in a thread I started or posted in.
- Mattermost DMs are a new delivery rule, separate from the `//dm` sigil.
- Breaker and kill files become per backend and per account.

**Pre-existing defects**, squawked on `mcp-server-discord-watcher:triage` #1–3:
- The oneshot doorbell loses messages on every re-arm, because it reseeds to the latest message.
- Doorbell mode never reports an unresolved identity.
- The poll loop is duplicated, and the copies have drifted.

**Idea:** `sqtk-doorbell.sh` is a hand-built second doorbell. Squawkie could be a third adapter.

## 4. Prior art

**Nobody has built the whole thing.**

**Loop guards: a converged pattern.**
- Mattermost Agents ignores bot posts unless they carry the `activate_ai` property, and turns tool use off for automated callers. **[src]**
- Hermes: 20 bot messages per 300 s per conversation, then 600 s of dropping. **[src]**
- OpenClaw: 20 per 60 s per bot pair. Matrix MSC4295: an `m.bounce_limit` hop counter.
- The layers: opt-in, a mandatory inline mention, a sliding-window budget, optionally a hop count.

**Claude Code channels** **[docs]**
- `notifications/claude/channel {content, meta}`, plus a permission relay that echoes request IDs.
- Gate on the sender's ID, not the room's.
- Custom channels need `--dangerously-load-development-channels`.
- **Claude Code refuses a channel server that negotiates MCP 2026-07-28.** Pin to 2025-11-25 or earlier.

**Trust**
- Mattermost bot `OwnerId` is required, and bots are disabled when their owner is.
- RFC 8693 `act`/`may_act` gives the shape for a signed mandate: subject = human, actor = agent, scope, expiry.
- Claude Code cross-session rule: a peer message never counts as consent; accept/hold/refuse.
- mcp_agent_mail: "discovery ≠ authorization", a contact handshake between organizations, TTL file leases.

**Floor control**
- No library exists. Open Floor Protocol (request/grant/revoke/yield, convener) and BFCP (RFC 8855) define the states, including **Revoked**.
- The papers say an addressed question binds the addressee to answer; otherwise an agent selects itself.

**Protocols**
- A2A v1.0 is strictly two-party, with no group or human identity. Don't carry it over chat.
- Steal from A2A: the Agent Card, the `Major.Minor` version header plus required-extension errors.
- From ANP: no silent downgrade. From MSC4564: a structured block inside a normal post.
- **MCP 2026-07-28 deprecates sampling.**

**Cross-org**
- Mattermost connected workspaces (Entry or Enterprise): two servers federate chosen channels, each keeps its own access control, and a share can't be re-shared to a third. Whether bots sync across is **unknown**.

**Recommendation:** Mattermost is the bus, carrying our own versioned envelope in post props with a
plain-text body always present.

## 5. Facts for the token broker (mattermost master `2de97aee`) [src]

**Bot permissions**
- Creating a bot needs `create_bot` (system scope), with `EnableBotAccountCreation` on (it defaults to false). The owner is forced to the caller.
- A bot token needs the caller to hold `create_user_access_token` **plus** `manage_bots` on a bot it owns (`read_bots` too, or it gets a 404). Revoking needs `revoke_user_access_token`.
- An image is set with `POST /users/{bot}/image`. **`/bots/{id}/icon` doesn't exist.**
- Team and channel adds are in default team and channel member roles.

**A non-admin broker is possible**
- The System Console permissions UI can't grant bot permissions.
- A system admin can patch the `system_user_access_token` role once, via `PUT /roles/{id}/patch` (allowed on Team Edition), to add `create_bot`, `read_bots` and `manage_bots`, then assign that role to the broker only.
- Catch: every account with that role gets bot creation.

**Other facts**
- Bots appear in @-autocomplete with a BOT tag.
- Bot↔bot and bot↔human DMs work. Under `RestrictDirectMessage=team` they need a shared team.

**Token expiry**
- Since **v11.9**, tokens take `expires_at`. Since **v11.10**: `MaximumPersonalAccessTokenLifetimeDays` and `POST /users/tokens/rotate`.
- Revoking a token doesn't close the websocket, but the next event or request fails and events stop.
- **The partner organization's production server runs a version older than 11.10** (checked 2026-10-19 via `x-version-id`), so it has no native expiry: broker revocation is the only expiry there.

**Claude Code `headersHelper`** exists for http, sse and ws MCP servers.
- It re-runs on each connect and **once after a 401/403**. It does not run on a timer.
- It gets `CLAUDE_CODE_MCP_SERVER_NAME` and `CLAUDE_CODE_MCP_SERVER_URL`.
- Project-scoped helpers have credential env vars stripped and need the trust dialog.
- So rotation works if the helper reads a token file the broker writes.
